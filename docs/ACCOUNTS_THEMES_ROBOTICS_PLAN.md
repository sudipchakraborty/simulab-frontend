# Accounts, subscription, themes and robotics implementation plan

## Accepted direction
User chose the existing React application and Node backend with reusable local/server modules and configurable defaults, and requested all modules including HX711 plus humidity sensing. No commit/push/deployment or live charge is requested. SMTP/payment credentials and QR image are not supplied; live delivery/charging must remain explicitly unconfigured.

## Architecture and contracts
- Keep the loopback hardware companion on4317 independent from account services on4320. Account API uses `/api/*`, persistent SQLite, scrypt password hashes, opaque hashed persistent HttpOnly session cookies, single-use expiring email verification and CSRF/origin controls. Never store plaintext passwords or browser bearer login tokens.
- Roles: admin, editor (default signup), viewer. Server permissions and ownership protect projects and administrative changes. Saving/export/autosave is disabled for trial/expired accounts, regardless of role, and is enabled only for paid subscriptions with write permission. Trial is configurable30days by default. No price is invented: checkout is unavailable until a positive price/currency and payment method are configured.
- SMTP module accepts host/port/TLS/user/password/from. Explicit development outbox stores email locally when SMTP is absent; no claim of delivered email. Email links validate the account once. Password reset/revocation and session logout are supported.
- QR checkout creates a server-owned pending payment. QR image is configurable later. Activation comes only from a validated payment-provider webhook or audited administrator confirmation; a client “paid” click never grants access. Payment adapters are injected and idempotent. No physical payment is initiated in tests.
- Theme IDs: corporate-navy (default dark), midnight, graphite, corporate-light, pearl, sand. Signed-in preference is persisted to a server JSON system config file and restored at launch; browser appearance cache is only a fast-start mirror. All white studio surfaces become semantic theme tokens. Monaco follows light/dark scheme.
- Account API JSON contracts: `GET /api/auth/session` -> `{user:null|{id,email,role,verified}, subscription:{mode:'trial'|'paid'|'expired',expiresAt}, permissions:string[], preferences:{theme}, csrfToken}`. Signup `{email,password,theme?}` -> pending-verification status; login `{email,password,remember:true}` sets cookie and returns session; logout POST; email verify GET; preferences GET/PUT `/api/preferences` `{theme}`. Projects GET/POST `/api/projects`, GET/PUT/DELETE `/api/projects/:id` with owner scope. Billing GET `/api/billing/config`, POST `/api/billing/checkout`, GET `/api/billing/payments/:id`, POST `/api/billing/payments/:id/submit-reference`, POST `/api/billing/webhook`. Admin users/role and payment approval routes require admin.
- API errors `{error,code?}`; unauthenticated session endpoint returns `{user:null,...}`. Frontend sends credentials and server-issued CSRF token on mutations; no role/entitlement authority in localStorage. Vite proxies `/api` to4320, configurable for tests. Session refresh on launch/focus and after payment.
- New circuit schema1.3 adds meters, HX711, DHT22, Nano, Mega2560, stepper/driver, servo, tactile/electromagnetic switch, generic6DOF/universal arm, Dobot Magician/uArm Metal educational profiles, conveyor, four-wheel car, IR emitter/detector. Existing schemas continue loading unchanged. Vendor mechanical profiles must be clearly approximate/configurable when exact geometry or protocols are unverified.
- Component categories exported from `src/circuit/categories.ts`: `CATEGORIES` and `componentCategory(kind)` with labels Microcontroller, Module, Robotics, Sensor, Actuator, Meter, Connection. Palette derives kinds from catalog.
- Board helper `src/circuit/boardRegistry.ts`: `mcuKinds`, `isMcuKind(kind)`, `boardTarget(kind)` -> uno/nano/mega2560/esp32s3/undefined and native board pin metadata. Nano classic executes real ATmega328P instructions; A6/A7 remain ADC-only/unverified. Mega gets a separately configured ATmega2560 runtime/firmware tests; never label Uno execution as Mega support.
- Pure models accept simulation microseconds and resolved volts. Add a bounded linear DC network solver for resistor/shunt meter paths, preserving floating/conflicting states. Meters do not fabricate current from voltage without a modeled branch. Actuator/robotic assemblies have explicit drivers/power and deterministic kinematics; vendor USB/serial compatibility is not implied. New sensor pin protocols must be driven by actual MCU reads/edges where integrated.

## Verification requirements
Auth: verify expiry/replay, password/session confidentiality, persistent remember-login, CSRF/origin, roles, ownership, privilege escalation, trial denial, paid expiry, config persistence, forged/replayed/amount-mismatched payment events. SMTP/QR/provider absence is visible; tests use explicitly labeled injected transports.
Models: DC voltage/current invariants; sensor frames/timing; power/logic bounds; stepper direction/enable, servo pulse/angle/slew, robot forward kinematics/limits, conveyor/car motion and optical pairing. Old editor/netlist/firmware suites remain green. Actual Nano/Mega fixtures prove chip/port/timer/UART behavior before support claims.
UI: signup/pending verify/login/session restore, themes across reload and account isolation, all trial save paths disabled (button, Ctrl+S, export and autosave), paid cloud ownership/save, payment pending vs verified, role controls and categorized library. Keep simulation and code state across tabs.

## Boundaries
No live email, charge, payment confirmation, QR upload, physical board operation or manufacturer-certified robot behavior can be claimed without evidence. Browser-only licensing cannot prevent an owner modifying their local JavaScript; server-side saves and private APIs are authoritative.
